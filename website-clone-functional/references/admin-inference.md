# admin 功能信息架构反推规则

没有后台 URL 时，`admin-ia.md` 的每一条都是从前台反推的"支撑这些前台功能至少需要什么后台"。它不是原站后台的真实形态，文档标题下必须写明这一点；用户给了后台 URL / 截图时，对应模块改为实采并写上 URL。

## 1. 三条反推公式

### 实体 → CRUD 模块

每个内容实体（Product / Article / Post / Category / Coupon…）一个管理模块：

| 部件 | 怎么写 | 来源 |
|---|---|---|
| 列表列 | 实体属性里适合一眼扫的（名称、分类、价格、状态、时间），≤ 8 列；密码永不出现 | 属性来源（实采）+ 挑选（推断） |
| 筛选 | 属性中的枚举 / 分类 / 状态 / 时间 / 评分；总有"关键词 + 创建时间" | 推断 |
| 批量操作 | 删除；可上下架的实体加"批量上下架"；需审核的加"批量审核"；用户 / 订单加"导出" | 推断 |
| 表单字段 | 全部属性 + 前台可见但 API 没给的（规格表、图廊、SEO 字段） | 实采 + 推断 |
| 校验 | 与前台表单一致的必填 / 格式；金额 / 数量非负；唯一性（slug、码） | 推断 |
| 状态流转 | 按实体类型套默认状态机（下表） | 推断 |

默认状态机：

| 实体 | 状态 |
|---|---|
| Product | 草稿 → 上架 ⇄ 下架；上架 → 售罄（库存） |
| Article / Post | 草稿 → 待审核 → 已发布 → 已下线 |
| Review / Comment | 待审核 → 已通过 / 已拒绝 → 已隐藏 |
| Order | 待支付 → 已支付 → 已发货 → 已完成；任一 → 已取消；已支付 / 已发货 → 退款中 → 已退款 |
| User | 正常 ⇄ 禁用 |
| Coupon | 未开始 → 生效中 → 已过期；任一 → 已停用 |
| Message（工单） | 待处理 → 处理中 → 已关闭 |
| Subscriber | 已订阅 ⇄ 已退订 |

### 用户行为 → 管理与报表

| 前台行为 | 后台模块 |
|---|---|
| 注册 / 登录 | 用户管理（查看、禁用、重置密码、导出）+ 角色与权限 |
| 下单 / 支付 | 订单管理 + 配送与运费 + 优惠券 + 报表（GMV / 转化） |
| 评论 / 评价 / 发帖 | 审核队列 |
| 联系表单 / 在线客服 | 留言 / 工单 |
| 邮件订阅 | 订阅者管理（导出到邮件工具） |
| 收藏 / 点赞 | 一般不需要独立模块；进商品 / 内容报表（收藏数） |
| 搜索 | 搜索词报表（热词、无结果词）——Could |
| 多语言 | 站点设置的语言开关 + 内容表单的多语言字段 |

### 固定模块（按站点类型裁剪）

| 模块 | 什么时候有 | 内容 |
|---|---|---|
| 仪表盘 | 总有 | 核心指标 + 待处理（待审核 / 待发货 / 待回复） |
| 角色与权限 | 总有 | 管理员账号、角色、权限矩阵、操作日志 |
| 站点设置 | 总有 | 基本信息、SEO 默认值、导航 / 页脚配置；有语言切换时加多语言 / 货币 |
| Banner / 推荐位 | 首页有 hero / 精选区 | 位置、素材、链接、排期、排序 |
| 日志审计 | 总有 | 登录日志、敏感操作日志 |
| 报表 | 有交易或统计脚本 | 见上表 |

## 2. 管理角色

默认三到四个：超级管理员（全部）、运营（内容 / 商品 / 营销 / 报表查看）、客服（订单查看与备注、工单、用户查看）、内容编辑（有 Article / Post 时：内容与审核）。多店铺电商加"商家后台"作为独立角色与入口（商家只看自己的商品 / 订单）。全部标推断。

权限矩阵：行 = 模块，列 = 角色，格 = 全部 / 查看 / 部分动作 / —。

## 3. 站点类型的裁剪

| 类型 | 加 | 减 |
|---|---|---|
| ecommerce | 商品 / 分类 / 订单 / 配送 / 优惠券 / 评价审核 / 报表（GMV） | 文章 |
| content | 文章 / 栏目 / 标签 / 评论审核 / 作者管理 / 专题 | 订单 / 优惠券 / 配送 |
| saas | 用户与团队 / 订阅计划与账单 / 功能开关 / API Key / 用量报表 | 商品 / 配送 |
| community | 帖子 / 话题 / 评论审核 / 举报处理 / 用户等级 / 禁言 | 订单 |

## 4. 有后台实采时

`crawl_features.py --admin-url <url> --storage-state state.json`（或用户在内联浏览器登录后逐页采）会把后台页面标 `type: admin`。后台页面的 `page.json` 通常有：`tables[]`（列表列名 = `headers`，行操作 = `hasActions`）、`forms[]`（编辑表单字段）、`navigation.side`（模块树）、`controls.filters/sorts/paginations`（列表筛选）。写 `admin-ia.md` 时：

- 模块树用 `navigation.side` 的实采链接，不用推断树
- 列表字段用 `tables[].headers`，标实采
- 表单字段用 `forms[].fields`，标实采
- 状态流转仍多为推断（除非筛选下拉里有状态枚举——那就是实采的状态集合）
- 前台反推出来但后台没见到的模块保留，标推断并注明"后台未见入口，可能在未采到的页面"

## 5. 常见误判

- **把前台的"我的订单"当后台**：`pageType=account` 是用户个人中心，不是 admin；只有 URL 含 admin / manage / dashboard / console 或用户指明的才是后台。
- **给静态内容建实体**：首页"三大卖点"、关于页团队介绍是 CMS 静态区块，归 Banner / 推荐位或站点设置，不建 Feature / Team 实体管理模块（除非列表 ≥ 6 项且有独立页面）。
- **过度设计**：后台反推只写支撑前台所需的最小集，不加原站没有证据的功能（积分、分销、多仓）；这些可以在 §5 待确认里提一句。
- **忘记密码字段**：用户管理列表 / 表单永远不显示密码；只有"重置密码"操作。
