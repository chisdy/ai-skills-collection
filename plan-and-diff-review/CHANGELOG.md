# Changelog

版本号写在 `SKILL.md` 的 `metadata.version`（Agent Skills 规范不支持顶层 `version` 字段，值必须是字符串）。

变更历史刻意放在这里而不是 `SKILL.md` 正文：`SKILL.md` 的每一行都会进入模型上下文，而历史对执行评审任务没有帮助。

## 1.0.0

首个版本。下面记录的是几个不显然的设计决策及其理由，便于将来回看时不重复推翻。

### 核心机制

- **范围分类**：每条发现必须归入 `Current Fix Required` 或 `Out Of Scope`，后者只报告、等用户批准，绝不写进计划或顺手实现。范围蔓延是这个技能存在的首要理由。
- **证据强制**：任何断言都要有具体观察支撑——读过的文件、codegraph 结果、grep 命中、或跑过的验证。从命名或记忆推断出的"应该处理了"是评审放过坏代码的主要途径。
- **必修项写回计划**：只活在聊天里的发现会随对话推进而丢失，等于评审白做。所以 `Current Fix Required` 必须以计划原有的结构和语言插入到正确阶段，并带可追溯标记（如 `补充于评审`）。这是本技能最独特的一步。
- **严重度分档**：`阻塞 / 重要 / 次要`，`必须补齐` 按此排序。平铺的必修项列表无法指导用户从哪下手。

### 命名与输入定位

技能名直接写出两种输入且顺序有意义：**计划在前，diff 在后**。评审尚未实施的方案是杠杆更高的场景——此刻发现的每个问题改起来都是零成本，实施后再发现就是返工。因此纯方案输入是本技能的主场，不是降级用法。

早期草稿曾命名为 `focused-fix-review`，问题在于 "fix" 暗示代码已经写完，而本技能最初的设计目标恰恰是评审方案计划，最独特的机制（写回计划文档）也以计划为中心。中途考虑过 `focused-change-review`，否掉的理由是 "change" 属于万能词，任何代码操作都是 change，把具体性换成了空泛。

相应地正文里：`Goal` 明确 *fix* 指被评审的那个解决方案（写成与否皆可）；步骤 1 要求把方案声称会触及的文件、符号、实体显式列入 `变更集`，因为方案的真实风险往往是它漏列的部分，而只有落到纸面才看得出漏了什么；步骤 2 说明对方案做同样的影响面映射；步骤 7 的验证拆成"代码已写成"与"方案未实施"两条路径。

### 评审与修复分离

划分 `[模式：评审]`（默认，只读，唯一可编辑的是计划文档）与 `[模式：修复]`（需用户批准具体的 `必须补齐` 条目）。不分离的话评审会静默变成打补丁，用户无法区分"发现了什么"和"改了什么"，也就无法审计。

由此派生两条规则：验证失败算一条带真实报错的 `必须补齐`，不是当场绕路修掉；以及刷新 codegraph 索引不算编辑（它写的是本地索引，不是仓库源码），避免模型被只读约束卡住不敢 sync。

### 变更集来源

步骤 1 要求先跑 `git status` / `git diff` 取变更文件与符号清单，而不是依赖对话里恰好提到的信息——静默改动正是评审要抓的东西。这个清单同时是步骤 2 的输入，并填入报告的 `变更集` 栏供用户确认评审对象没跑偏。

### 方案未实施时的验证

纯方案没法 type-check，所以验证改为核对前提：它假定存在的符号、字段、表、端点、配置键要逐个读出来确认；假定的起始状态（当前行为、已有数据形态、已应用的迁移）要和现实对齐；并为每条步骤说明将来靠什么检查证明其正确——无法验证的步骤本身就是一条 `必须补齐`，因为它要么描述不足要么不可测。

### codegraph 索引状态三档诊断

不是"可用 / 不可用"两分。实测 `codegraph_status` 的失败有三种成因，报错长得像但需要相反的应对：

| 成因 | 应对 | 理由 |
|---|---|---|
| 索引存在、server 找不到（报错提到 working-directory / workspace-root，并自称索引大概没问题） | 带显式 `projectPath` 重试 | 实测一次调用即恢复完整索引（338 文件 / 4193 节点）。为此重建是纯浪费。注意 `~/.claude.json` 的 codegraph 配置没有 `--path`，比 Cursor 更容易撞上这种误判 |
| 索引存在但过期 | 自动 `codegraph sync` | 只处理增量、无新副作用。这一档对评审尤其重要：落后于索引的文件通常正是待评审的那些 |
| 从未初始化（无 `.codegraph/`） | 停下来问用户，给出文件数作为规模信号、`codegraph init --index` 命令、gitignore 提醒 | 耗时不可预估（本机已有索引体积 720K 到 1.4G）、副作用可能上 G、且 `codegraph init` 不保证把 `.codegraph/` 加进 `.gitignore`（抽查三个项目有一个没加）。仅在用户拒绝后才降级到 Grep + Read 并标注覆盖较弱 |

MCP 层只暴露了 9 个只读查询工具，没有建索引入口，所以建索引必须走 Shell——这是它需要用户批准的另一个理由。

反模式表里 `"codegraph 慢，先跳过"` 的反驳写明 sub-millisecond 只对**查询**成立且以索引已存在为前提，避免被当成"建索引也很快"的依据。

### 其他

- 语言约定：正文指令用英文，交付的评审报告用简体中文，模板小节标题固定以便用户跳读。
- 输出顶部是一句话结论（`可以合并 / 需补齐 N 项 / 需返工`），否则用户要读完六个小节才知道能不能交。
- `Plan source priority` 按仓库自身约定探测计划目录，不写死路径。
- codegraph 用法说明保持精简，不复述 MCP server 自带的 tool-selection 指引。
