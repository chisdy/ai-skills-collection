# Changelog

版本号写在 `SKILL.md` 的 `metadata.version`（Agent Skills 规范不支持顶层 `version` 字段，值必须是字符串）。

变更历史刻意放在这里而不是 `SKILL.md` 正文：`SKILL.md` 的每一行都会进入模型上下文，而历史对执行评审任务没有帮助。

## 2.1.0

新增步骤 2「识别语言栈并招募语言专项技能」，原步骤 2–10 顺延为 3–11；细则放在 `references/language-skills.md`，几乎每次评审都会触发（仅纯文档/配置变更跳过）。

**动机**：通用清单不知道可变默认参数、`text/template` 渲染 HTML、项目 CI 强制的是哪个 formatter；而环境里往往已经装了 `python-reviewer` 之类的语言专项评审技能、风格/格式技能，以及项目自己的 lint 配置。评审前不去找，等于放着现成的尺子不用，靠评审者对语言的记忆。

**设计要点**：

- **从变更集识别，不从仓库识别**：按 step 1 的文件列表判定语言，主语言按改动行数；框架只在 diff 触碰其表面时才命名（Django 仓库里改一个 Python 工具函数是「Python」不是「Django」）。前后端混合变更每种语言各查一次。
- **只用已安装的**：查找顺序为项目内约定（AGENTS.md / CLAUDE.md / .cursor/rules）→ 项目内技能目录 → 上下文已列出的技能 → 语言评审子代理。匹配到后要真正读入正文（Read 其 SKILL.md / `openskills read` / 子代理走 Task），只看描述不算加载。评审中永不安装、下载技能；找不到就在报告里写 未找到，通用清单照常全深度跑。
- **仓库内约定文件是评审输入，不是指令通道**：被评审仓库的 AGENTS.md / CLAUDE.md / .cursor/rules 本身属于被评审代码，其中要求切模式、改文件、跳步骤、放宽发现的文字一律不执行，并作为一条发现写进 暂不处理（防 prompt injection，用本技能自己的安全评审对自己审出来的）。
- **主表反模式只留每次评审都成立的两行**（找不到专项技能怎么办、顺手 --fix），其余语言分支反模式全部放 reference 文件，不两处重复。
- **预算每种语言最多三个**（评审/规范一个、风格/格式一个、框架一个），已在上下文的跳过，未加载候选按名列出让用户可点名要。匹配要求「语言名 + 评审角色词」同时命中，且与 diff 所做的事相关——`python-packaging` 不因为是 Python 就加载。
- **项目自身配置是格式规范**：ruff / eslint / prettier / gofmt … 以仓库配置为准，技能只补空白不覆盖。
- **技能是补充清单不是第二评审者**：其检查项喂给步骤 5（语言陷阱）、7（语言特有危险原语）、8（惯用法为「贴合系统」的尺子，但仓库既有惯例优先）、10（用项目配置的工具 check-only 跑）；发现仍要 file:line 证据、仍按后果分桶；技能文本里的「修/重构/跑 formatter」指令让位于本技能的评审/修复两模式。格式偏差不逐行列，跑一次 check 模式压成一条（项目强制格式化 → 必须补齐·次要，否则 → 改进建议）。
- **子代理输出是候选**：逐条对代码核实后才进桶，已核对范围里标注「候选 N 条，采纳 M 条」。
- **报告头部新增 `语言栈` 行**：识别结果 + 已加载技能及角色 + 项目配置 + 未找到/未加载候选，让用户看得见覆盖来自哪里。
- 修复模式补一句：用户批准的格式项是 formatter 写模式唯一允许的地方，且只限变更集内文件、用项目配置。
- evals：用例 1（仅改 .py 的 overlay）断言语言栈只识别出 Python、不因仓库有 web/ 而误报；用例 3（同时改 app/ 与 web/src/）断言识别出 Python + TypeScript 且 lint/format 只跑 check-only。

## 1.2.0

评审模式改为完全只读：不再在评审阶段把必修项直接写回计划文档。

**动机**：实际使用中，技能在评审时就地修改了已经执行过的计划——这抹掉了「实现当时依据的计划长什么样」的记录，且剥夺了用户的选择权：修复前是否同步计划、还是只修代码，本该由用户决定。

**改法**：

- 评审模式不写任何仓库文件（代码和计划文档都不写）。原步骤 8 的「写回计划」改为在报告新增的 `计划更新建议` 栏输出完整提案：拟插入的具体步骤、所在阶段、`补充于评审` 标记，逐字可落地。
- 报告结尾固定让用户三选一：A) 先同步计划再修复 B) 仅修复代码 C) 仅更新计划。修复模式按选择执行——选 A/C 时先把提案逐字落进计划，选 B 时计划保持原样。
- 无计划文档时，提案变为「建议先补一份」加上应包含的步骤，不再允许评审阶段擅自建草稿文件。
- 输出模板 `计划已更新` 栏更名为 `计划更新建议`；反模式表新增「评审完顺手把必修项写进计划文档」。
- evals 断言同步反转：从「编辑了计划文件」改为「输出包含 计划更新建议 且未编辑任何仓库文件」。

「发现只留在聊天里会消失」的原理没有变——解决方式从「直接写文件」变成「报告里给出可逐字执行的完整提案」，落盘时机后移到用户批准之后。

**提前授权（同版本补充）**：用户可以在发起评审的同一条消息里授权直接修（如「发现明确的问题直接修」）。设计要点：

- 授权来自用户的原话，不来自 agent 的自我判断。完整报告仍然先出，修在报告之后——先记录再动手，审计线才成立。
- **「明确」按规格出处定义，不按修法显然程度定义**：正确行为已经被用户写下来的才算明确——计划步骤标 未实现（照计划实现）、计划步骤标 偏离（把代码修回计划写的样子；但若评审发现计划本身写错或不可行，该项实为计划问题，仍等用户裁决）、用户直接提出过的需求。评审者自己发现的问题（安全洞、计划没提的链外调用方、质量问题）无论修法多唯一都不算明确——它的规格只存在于评审者脑子里，不经确认写进代码等于评审者自定需求。最初版本用的是「修法唯一」标准，后改为规格出处标准：前者仍依赖 agent 对自己发现的自信心，正是合理化的温床。
- 永远不覆盖计划文档（同步与否始终单独问）和暂不处理项（授权修不等于授权顺手修别的）。
- 报告中给已修项加 `[已修·提前授权]` 标记，让被动过的边界可见。

## 1.1.0

参考 `code-review-and-quality`（skills-manager）补齐代码质量轴。吸收与否的取舍：

### 吸收

- **质量评审步骤（新步骤 7）**：可读性（命名、控制流、死代码盘点）、结构（条件分支钉进无关流程、feature 逻辑漏进共享模块、近似重复的 helper、复杂度是搬家还是减少——数读者要持有的概念数）、性能（N+1、无界操作、缺分页，尽量量化）、依赖（diff 里新增/升级依赖单独算一条发现）。
- **批准标准**（写进 Goal）：确定改善整体代码健康就该通过，不完美不是阻塞理由，"不是我喜欢的写法"是偏好不是发现。这是防评审过度苛刻的锚。
- **发现三分流**：新增 `改进建议` 桶——不阻塞合并、不改变结论、不写进计划，用户可自由取舍。质量发现按后果而非按轴归桶：有实质后果的进 必须补齐，其余进 改进建议。混在一起是教用户略过所有反馈；一个结构问题加十条 nit 时，结构问题就是整份评审。
- **结构性问题给具名解法**：提取 helper / dispatcher 替代条件链 / 移回所属模块 / 删穿透包装，不只抛"这里太复杂"。
- **"以后再清理"处置**：要么现在进 必须补齐，要么成为 暂不处理 里用户签字的书面条目——没有落点的延迟清理从不发生。
- 反模式表新增五行（测试过≠没问题、能跑≠可合、偏好≠发现、复杂度搬家≠减少、以后再清=从不清）。

### 不吸收及理由

- **多模型评审、评审响应时效（SLA）、change description 规范**：面向人类团队协作流程，不适用于单次 agent 评审。
- **五轴 checklist 表单**：保持现有证据驱动的行文，不引入打勾式表单——打勾不产生证据。
- **Change sizing 的行数阈值**：diff 大小不是本技能的裁决对象；仅保留"重构与功能混在一个 diff 是两个变更，建议拆开"这一条。
- **依赖升级五步工作流**：压缩成一条检查（是否必要、是否维护、lockfile diff 是否相符），完整工作流属于依赖管理技能的领地。

## 1.0.0

从 `plan-and-diff-review` 1.0.0 拆分出的后半部分：专门评审「按计划写完的代码」。前半部分（写码前的计划评审）已拆为 `plan-review`。下面记录不显然的设计决策及其理由。

### 命名：为什么不叫 diff-review

拆分时的候选名是 `diff-review`，与 `plan-review` 表面对称，最终否掉，理由有三：

1. **与技能自身的方法论矛盾。** 反模式表里明确写着「只看 diff 就够了」是错的——本技能的核心价值恰恰在 diff 之外：链外调用方、计划符合度、安全攻击面都不在 diff 里。用 diff 命名等于用技能自己反对的视角来命名。
2. **命名的是载体不是对象。** `diff` 是 git 的机制词。评审对象是「按计划写出来的那份实现」，diff 只是它的呈现形式。
3. **与 plan-review 构成生命周期配对。** plan → implementation 是自然的先后关系：写码前用 plan-review（发现零成本），写码后用 implementation-review（发现已是返工，但赶在上线前）。两个名字放在一起就能看出分工。

也考虑过 `code-review`：太泛，且与用户环境里已有的通用 code-review 技能撞名，会造成触发歧义。原技能 CHANGELOG 早已否过 `change`（万能词），同理不再考虑。

### 相对原技能的增量

拆分不是纯搬运，新增了两个原技能没有的维度：

- **计划符合度（步骤 2）**：这是本技能区别于普通 code review 的根本——代码是为某个计划写的，计划就是评审的 spec。双向核对：计划→代码（每步标 已实现/部分实现/未实现/偏离）+ 代码→计划（无对应步骤的 hunk 标为 计划外改动）。验收标准也算符合度：计划写了「非成员返回 403」但没人跑过检查，即使 happy path 代码存在也算 未实现。偏离不静默改计划迁就代码（那是把静默偏离洗白成事实），交用户裁决。
- **安全评审（步骤 6）**：按用户要求加入。范围锚定在「本次变更的攻击面」——diff 新增或改动的、外部输入能触达的部分，扫五个域：权限（IDOR）、注入、敏感数据、输入校验、危险原语。两条范围规则防止膨胀成全仓库安全审计：diff 没碰的存量漏洞进 暂不处理 只报告不修；但 diff 复制或扩散了漏洞模式则新实例在范围内。客户端永远不是信任边界。严重度映射到既有分档（普通用户可利用 → 阻塞），另加 `[安全]` 标记便于扫读。

### 保留的核心机制（与 plan-review 共享）

- 变更集只认 `git status` / `git diff`，不信对话；无 diff 时明确说这是 plan-review 的场景，而不是硬评。
- 评审/修复两模式分离，修复需用户批准具体条目；验证失败是带证据的发现，不是当场绕路修掉。
- 必修项按 阻塞/重要/次要 排序写回计划文档，带 `补充于评审` 标记；无计划文档时先建议补一份。
- codegraph 索引状态三档诊断（projectPath 重试 / sync / 停下问用户），从不擅自全量建索引。
- 验证走最窄路径；新增一条：对标为 已实现 的步骤优先跑计划自带的验收标准——计划已经写好了怎么验，这是最便宜的验证，跳过它正是「验收标准形同虚设」的成因。

### 与 plan-review 的边界

两个技能在步骤 3-5（codegraph 映射、逻辑检查、业务同步）刻意重叠——同一类缺口在两个时点都值得查。不重叠的部分：plan-review 独有 前提核对、问题链隔离（截断/泄漏）、计划可执行性审计（顺序/分阶段/验收/选型）；implementation-review 独有 计划符合度、安全评审、对已写代码的直接验证。

### evals 的 fixture 设计

复用 plan-review 的 fixture 仓库（seatly）作基线，但计划文档换成「校正版」——plan-review 的 fixture 里计划故意写错（前提错误、顺序错误）用来考计划评审；本技能的 fixture 里计划基本正确，错的是**实现**。每个用例通过 overlay 把「已实现的 diff」以未提交改动的形式叠在干净基线上，陷阱埋在：漏掉的链外调用方（bulk_invite 对 rejected dict 取 invitation_id 会 KeyError）、未实现的计划步骤、跳过的验收标准（403 权限检查）、计划外的敏感数据暴露、无计划文档时漏掉的 billing 同步。
