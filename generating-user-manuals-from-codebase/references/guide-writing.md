# 单篇指南写作规范

阶段 4 逐篇撰写时的完整规则。SKILL.md 只保留硬规则摘要，细则以本文为准。本文的示例用中文，实际输出语言按阶段 0 确认的结果（跟随项目 UI 语言或用户指定）。

## 0. 目标

把已验证的产品事实转成任务导向的操作说明，读者不需要知道实现就能照着做。每一个具体的界面标签、权限、限制、状态流转、结果都是**事实断言**：只有事实台账里有证据支撑时才写进正文。

质量测试只有一句：读者能否知道**这个任务是否与自己有关、该做什么、成功长什么样、会出什么错**——且不遇到编造的细节或内部工程词汇。

## 1. 事实台账

写正文之前，每篇指南先在 `_inventory.md` 对应行（或工作笔记）里确认下表七类事实都有来源。台账不进正文，除非用户要求。

| 类别 | 记什么 |
|---|---|
| 读者与目标 | 谁在操作、要得到什么结果 |
| 已验证的入口 | 确认过的页面、菜单、导航路径 |
| 已验证的动作 | 点击、输入、选择、确认 |
| 已验证的结果 | 成功信号、结果状态、下一步去处 |
| 权限与变体 | 谁能做、不同角色的路径差异 |
| 风险与恢复 | 不可逆影响、失败表现、重试路径 |
| 未知项 | 缺失的标签、限制、格式、时间、保留期、权限 |

### 来源优先级（冲突时按此顺序取）

1. 界面实采（`browser_snapshot` / 截图）或明确的验收标准
2. 项目里现有的产品文档
3. 当前实现行为（代码里的校验、枚举、错误映射）
4. 设计稿或需求说明
5. 推断

推断永远不能悄悄升级为事实。来源冲突时，在编辑备注里写明冲突，不要无依据地选一边。

## 2. 写作流程

1. 确定读者、任务、预期结果。
2. 只把有支撑的事实抄进台账。
3. 把实现概念翻译成用户可观察的语言。
4. 按任务组织，不按页面或内部模块组织。
5. 前置条件放在步骤前，成功信号放在步骤后，警告紧贴风险动作之前。
6. 交付前跑一遍 §6 的两项检查。

关键信息缺失且用户允许提问时，只问会实质改变操作说明的问题。用户要求直接出稿时，先写已验证的部分，未决事实放到正文之后的独立编辑备注里。

## 3. 翻译规则

描述用户看到和经历的东西：

| 内部材料 | 用户视角写法 |
|---|---|
| 接口或组件名 | 已确认的页面或动作（若已知） |
| `processing` | 文件正在处理中 |
| `ready` | 文件已可使用 |
| `failed` | 处理失败；按已验证的恢复动作操作 |
| 后台任务 / 队列 | 系统会在后台继续完成该任务 |

不暴露路由、组件名、数据库字段、内部枚举、服务边界、实现原理——除非读者是技术人员且确实需要。

**不要从代码标识符推断界面文案。** `UploadAssetDialog` 只能证明存在一个上传界面，不能证明按钮上写着"上传素材"。标签不明确时用中性动作（"打开上传入口"）或标记待验证。阶段 1 里 i18n 文件、模板字面文本是文案的合法来源；变量名、组件名、路由名不是。

不要从行业惯例推断支持的文件类型、限制、默认值、权限、时间、保留期、自动通知或恢复行为。

## 4. 单篇结构

按功能取舍，没有价值的节直接省略。对应模板见 `assets/templates/feature-guide.md`。

```markdown
# [用户目标或功能名]

[一段话：这个功能帮读者完成什么。]

## [开始之前]

- [已验证的权限、前置条件或所需材料]

## [完成主要任务]

1. [使用已验证的可见文案描述动作。]
   ![alt：界面状态 + 被标注的动作](assets/<feature-id>/01-<step>.png)
2. [下一步动作。]
3. [确认或提交。]

**结果：** [可观察的成功信号与下一步。]

## [变体或后续任务]

[仅当有证据且有用时保留。]

> **[警告标签]：** [紧贴风险 / 不可逆动作之前写后果。]

## [出现问题时]

- **[可观察的现象]：** [已验证的恢复动作。]

---

## [编辑备注标题——不属于用户正文]

- [缺失的事实以及它为什么重要]
```

方括号内是占位说明，用输出语言替换成实际标题。编辑备注放正文之外；不要把每个未知都变成 FAQ；没有实质未知就省略编辑备注节。全书的编辑备注在阶段 5 汇总到 `_editor-notes.md`。

## 5. 角色与变体

角色路径相同时写一份共用指南；访问权限、可用动作或后果不同时，用紧凑的权限表或分角色小节。

重要边界写两面：谁可以执行，其他读者该怎么办。不发明证据之外的角色能力。

破坏性或改变访问权限的动作：

- 写明谁可以执行；
- 把后果放在确认步骤旁边；
- 写明受保护的角色或例外；
- 只在有证据时建议更安全的替代方案。

## 6. 交付前检查

### 证据检查

- 引用的每个标签和导航路径都有支撑。
- 每条限制、权限、格式、时间、保留期的断言都有支撑。
- 每条成功、失败、重试行为都有支撑。
- 没有内部标识符和实现细节（除非必要）。
- 未知项以编辑备注形式分离，没有伪装成事实。

### 可用性检查

- 标题描述读者的目标。
- 前置条件在任务之前。
- 每个编号步骤只有一个主要动作。
- 写了成功长什么样。
- 角色差异一眼能扫到。
- 警告在决策点，不在远处的通用说明里。
- 排障从可观察的现象出发，只给已验证的恢复动作。

截图相关检查见 `screenshot-annotation.md` §6。

## 7. 常见错误

| 错误 | 纠正 |
|---|---|
| 用"看起来合理"的界面标签填空 | 用中性措辞，或在编辑备注里标待验证 |
| 把工程说明换个友好语气重述 | 围绕读者的任务和可观察结果重新组织 |
| 把未知项当 FAQ 答案发布 | 移到独立编辑备注 |
| 按页面罗列而不是按任务 | 按读者想完成的事分组 |
| 把破坏性后果藏在通用说明里 | 警告紧贴确认步骤之前 |
| 从一条已知限制推断整套角色权限 | 只写已验证的边界 |
| 一张截图里标注五六个点 | 拆成两步，各配一图 |
