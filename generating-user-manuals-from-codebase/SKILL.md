# Generating User Manuals from Codebase

把一个项目的代码和界面变成用户能照着做的手册。方法是先采证再写：每条界面文案来自 i18n / 模板字面文本 / 界面实采，每条限制与权限来自校验规则或守卫代码，写进正文的每个断言都能指回功能清单的证据列；找不到证据的进编辑备注，不进正文。产出是 Markdown 手册（可适配 VitePress / Docusaurus / MkDocs）加带标注的截图。

本技能**不**写 API 文档 / 开发者文档（那是代码注释与 OpenAPI 的事）、**不**写 PRD 或信息架构（用 `website-clone-functional`）、**不**改产品代码。读者是最终用户与管理员，不是开发者。

## 入口模式（按用户措辞判定，开头告知选了哪种）

| 用户在说 | 模式 | 起止阶段 |
|---|---|---|
| "给这个项目 / 系统生成用户手册、帮助中心、使用说明" | **全量** | 0 → 5，阶段 3 末停一次等大纲确认 |
| "先梳理有哪些功能、出个手册大纲 / 目录" | **仅大纲** | 0 → 3，产出 `_inventory.md` + `_outline.md` 后结束 |
| "按这份大纲 / 这些事实 / 这个截图写帮助文档"、"把 X 功能写成一篇帮助文章"、"按 `_outline.md` 继续" | **仅撰写** | 4 → 5，以用户给的大纲或磁盘上的 `_outline.md` 为准，不重跑分析 |

用户没说清时按全量处理。三种模式共用同一套问卷、硬规则、模板与截图规范。

## 最小问卷（缺什么问什么，一次问完）

1. **产品与读者**：Web / 移动 / 桌面 / CLI？读者是最终用户、管理员，还是两者？有哪些角色？
2. **范围**：整个产品，还是指定模块 / 功能？已有手册要更新还是从零写？
3. **输出**：语言（默认跟随项目 UI 语言）；格式——单文件 / `docs/manual/` 多文件 / VitePress / Docusaurus / MkDocs（默认多文件 Markdown）。
4. **能否运行**：项目能在本地跑起来吗？需要登录吗——用户自己在内联浏览器里登录；有测试账号 / 测试环境吗（决定能否验证删除等危险操作）？
5. **确认方式**：大纲出来后要不要停下确认（默认要）。

仅撰写模式只问 3；用户已提供的答案不重复问。

## 五阶段流程

```
0 范围确认 → 1 代码发现 → 2 界面验证 → 3 手册大纲 ⏸ 用户确认 → 4 逐篇撰写与截图 → 5 QA 交付
```

工作产物统一放用户项目的 `docs/manual/`（用户指定则改）：`_inventory.md`（功能清单）、`_outline.md`（大纲）、`_editor-notes.md`（编辑备注汇总）、`assets/<feature-id>/`（截图）、正文各篇。下划线开头的是工作文件，不是发布内容。

### 1. 代码发现 → 功能清单

识别技术栈（`package.json` / `pubspec.yaml` / `go.mod` / 框架目录），按 `references/evidence-sources.md` 的查找表提取六类证据，填 `_inventory.md`（模板 `assets/templates/feature-inventory.md`）：

| 证据 | 找什么 | 能证明什么 |
|---|---|---|
| 功能与入口 | 路由表、菜单 / 导航配置、CLI 命令注册 | 功能存在、入口路径 |
| 界面文案 | i18n 文件、模板 / JSX 字面文本 | 按钮 / 标题 / 提示的**实际文字** |
| 权限与角色 | 路由守卫、`hasPermission` / `can()`、RBAC 配置 | 谁能进、谁能做 |
| 限制 | zod / yup / 表单 `rules`、`accept` / `maxLength`、后端校验 | 文件类型、大小、长度、数量 |
| 状态与流转 | 枚举 + 展示映射、状态机 | 有哪些状态、界面怎么显示 |
| 错误与恢复 | 错误码映射、toast / message 常量 | 出错时用户看到什么 |

每行记功能 ID、名称、入口、角色、状态、限制、证据（`文件:行`）、验证状态（`仅代码`）。已有 README / docs / CHANGELOG 里的产品描述可作第二级来源。**代码标识符只能证明"存在"，不能证明"文案"**：`UploadAssetDialog` 不等于按钮叫"上传素材"，文案必须来自 i18n、字面文本或实采。

### 2. 界面验证 → 实采

能运行就跑起来（按 `references/ui-verification.md` 检测启动方式，用户自己登录），逐个功能：导航到入口 → `browser_snapshot` 记真实标签与状态 → 触发（只做只读或本地 / 测试环境允许的操作）→ `browser_snapshot` 记结果 → 需要时截一张原始帧备用。回填 `_inventory.md`，验证状态改为 `实采`。不能运行的保持 `仅代码`，写进编辑备注。

**零写操作纪律**：非本地、非测试环境，不提交任何会产生持久数据的操作（创建、删除、支付、发送）。危险操作只在用户确认是测试环境时验证，否则只写代码里能证明的部分。

### 3. 手册大纲 → 用户确认（关卡）

按 `references/manual-structure.md` 的四架书内容模型生成 `_outline.md`（模板 `assets/templates/manual-outline.md`）：两级目录；每节标所属书架、来源功能 ID、验证状态、截图计划（截哪个时刻、标注什么）、必备节勾选；按角色拆分的决定；未决问题。

然后在聊天里给**确认摘要**——节数、覆盖功能数 / 清单总数、没有截图的节、未决问题、角色拆分决定——**并结束本轮回复**。不要在同一轮继续写正文。用户可以口头确认或修改、直接编辑 `_outline.md`、或把头部 `status: draft` 改成 `confirmed`。用户在问卷里明确说不用确认时跳过停顿，但大纲文件照样写。

### 4. 逐篇撰写与截图

**以磁盘上的 `_outline.md` 为唯一依据**重新读取（不用记忆里的版本）；`status` 仍是 `draft` 且用户没有口头确认时，先提醒再继续。按大纲顺序逐篇写，规则在 `references/guide-writing.md`：前置条件 → 编号步骤（一步一动作）→ 结果 → 变体 → 出错处理；警告紧贴风险动作之前；角色差异用权限表或分节；未知项进编辑备注。

截图按 `references/screenshot-annotation.md`：走到该步 → 注入 `scripts/collect/annotate.js` 给目标元素加高亮框 / 编号角标 / 遮罩 → `browser_take_screenshot` → `clear()` → 存 `assets/<feature-id>/<nn>-<step-slug>.png` → Markdown 里文字在前、图在后、必带描述性 alt。一图一焦点，单图标注 ≤ 4，多步流程只截入口 / 关键动作 / 结果 2–4 帧。

### 5. QA 交付

- [ ] 覆盖率：`_inventory.md` 每行都映射到大纲某节；大纲每节都已成文（或明确标"本版不含"）
- [ ] 证据：正文里每个标签、路径、限制、权限、状态、恢复动作都能指回清单的证据列；没有路由、组件名、字段名、内部枚举
- [ ] 未知项全部在 `_editor-notes.md`，正文里没有"通常 / 一般 / 可能支持"
- [ ] 截图：每图有 alt、一图一焦点、标注 ≤ 4、无真实用户数据 / 密钥 / 内部 URL、引用路径存在
- [ ] 结构：每页只属一架书；每类页面的必备节齐全；标题动词开头；两级导航
- [ ] 格式：按问卷选的格式输出（sidebar 配置片段见 `manual-structure.md` §5）
- [ ] 交付语写明：模式、覆盖 N/M 个功能、实采 / 仅代码各多少、缺截图的节、编辑备注条数

## 硬规则（三种模式都适用）

1. **文案只认三种来源**：i18n 文件、模板 / JSX 字面文本、界面实采。标识符、注释、变量名不算。
2. **限制与权限只认代码或实采**：不从"常见产品都这样"推断文件类型、大小、默认值、保留期、通知、权限。
3. **推断不升级为事实**：来源冲突写进编辑备注，不选边。
4. **零写操作**：非本地 / 非测试环境不做任何写操作；点任何按钮前先 `browser_snapshot` 确认它不是提交 / 删除 / 支付。
5. **大纲关卡**：全量模式必停一次；仅撰写模式必以磁盘 `_outline.md` 为准。
6. **编辑备注不进正文**：未知项、待确认标签、冲突全部放 `_editor-notes.md` 与各篇末尾的编辑备注节。
7. **不暴露实现**：路由、组件名、字段名、枚举值、服务边界不出现在正文，除非读者是技术人员且确实需要。

## 常见误判

- **把组件名当按钮文案**：`ExportButton` → "导出"是推断；去 i18n 或模板里找实际文字。
- **把路由守卫当完整权限模型**：`requiresAdmin` 只证明这条路由需要管理员，不证明其他角色不能通过别的入口做同一件事。
- **把前端校验当唯一限制**：后端可能更严（或更松）；两边都查，冲突进编辑备注。
- **把 i18n 里所有 key 当已上线功能**：可能是废弃文案；以路由 / 菜单能到达的为准。
- **把 feature flag 后面的功能写成默认可用**：查 flag 默认值，写清"若已启用"或不写。
- **把"仅代码"的状态写得像实采**：没在界面上看到过的状态，措辞用"系统会显示为…（待验证）"并进编辑备注，或不写。
- **每步一张截图**：读者要的是找到位置，不是看幻灯片；2–4 帧关键点。
- **大纲一出就接着写**：全量模式必须停下，哪怕大纲看起来很明显。
