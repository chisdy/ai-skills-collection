# Changelog

版本号写在 `SKILL.md` 的 `metadata.version`。变更历史与设计决策放这里，不进 `SKILL.md` 正文。

## 1.0.0

首个版本。前身是一份只管"把已知事实写成单篇功能指南"的写作规范（`creating-product-feature-guides`，未发布），本版在它前面补上范围确认、代码发现、界面验证、手册大纲四个阶段，使其能从项目代码与运行界面直接生成整本手册。原写作规范整体迁入 `references/guide-writing.md`，作为阶段 4 的细则。

### 为什么把写作规范下沉为一个阶段，而不是让它继续做 skill 主体

原规范的核心价值——每个标签、限制、权限都是需要证据的事实断言；不从组件名推断文案；未知项进编辑备注——是对的，但它假设事实"由别人提供"。用户真正的场景是"这个项目在这里，帮我写手册"，事实要 agent 自己去挖。挖的方法（去哪找路由 / i18n / 守卫 / 校验、怎么跑起来看界面）才是整个流程里最费上下文的部分，所以它们成了 SKILL.md 主体，写作细则退到 references。

### 为什么文案只认 i18n / 字面文本 / 实采三种来源

从代码生成手册最常见的失败是：看到 `UploadAssetDialog` 就写"点击**上传素材**"。组件名、变量名、路由名是开发者的命名，用户看到的是 i18n 文件或模板里的字面文字。`evidence-sources.md` §2 把文案来源限定为这三种，其余一律算推断；i18n 里有多个候选 key 时也不挑，标 `待实采`。这条规则成本很低（多 grep 一次），却能消掉一大类错误。

### 为什么先出功能清单再写

手册最常见的问题不是写错，是漏。`_inventory.md` 让"覆盖率"可检查：每个功能 ID 要出现在大纲某节的来源列里，否则进"本版不含"并写理由。清单同时是证据台账——正文里每个断言都能指回一行的证据列，阶段 5 的证据检查才有落点。

### 为什么大纲是强制确认关卡

改大纲的成本是改几行表格；改正文的成本是重写多篇加重截图。手册的结构决策（按任务还是按角色分组、哪些功能不写、哪些节没有截图）是用户的判断，不是 agent 的。所以全量模式在阶段 3 末尾必须结束回合，等用户确认或修改 `_outline.md`。用户在问卷里说"不用确认"时不停，但大纲文件照样写——它仍是阶段 4 的唯一依据。

### 为什么不拆成大纲 / 撰写 / 总控三个 skill

曾考虑仿 `website-clone` 三件套。没拆的原因：

- 确认动作发生在对话层——agent 结束回合、用户回复——不需要 skill 边界来承载。状态在 `_outline.md` 文件里，跨对话恢复走"仅撰写"模式即可。
- 拆开后 `_inventory.md` / `_outline.md` 会从内部工作产物变成两个 skill 之间的契约，字段改动要两边同步；仓库约定零跨目录引用，问卷、硬规则、截图规范要在每个目录各放一份。
- "只要大纲不要正文"作为独立需求很弱；"只按事实写文档"就是原 skill 的能力，用"仅撰写"模式保留即可。
- 这里的编排是线性的，总控会是几十行胶水。

改为一个 skill 三种入口模式（全量 / 仅大纲 / 仅撰写），仿 `apple-hig-design` 的多模式写法。拆分的触发条件：后续版本给分析阶段加入代码扫描脚本，且出现"只要功能清单"的独立需求时，再把分析半边拆出去（两个 skill，无总控）。

### 为什么标注用 DOM 覆盖层而不是图像后处理

`scripts/collect/annotate.js` 在页面上叠一层 fixed 定位的框 / 角标 / 遮罩，然后用浏览器工具截图，截完清除。相比截图后用 Pillow 画：

- 两条浏览器路径（cursor-ide-browser 的 `Runtime.evaluate`、Playwright MCP 的 `browser_evaluate`）都能注入，零 Python 依赖。
- 标注目标是选择器而不是像素坐标，界面改版后重截只需重跑同一组参数。
- 覆盖层不改目标元素样式，`pointer-events: none`，不影响后续交互。

代价是原生 `confirm()` 弹窗截不到标注（用引用块代替），以及不能画箭头——按截图规范箭头本来就不推荐（一个目标用框，多个用编号）。Pillow 后处理留作后续可选项。

### 为什么截图规范限制"2–4 帧、单图 ≤ 4 标注、一图一焦点"

来自技术文档写作的通行实践（Ritza 样式指南、Google 开发者文档样式、ScreenGuide / Haiku / Archbee 的截图指南）：读者看图是为了找到位置，不是看幻灯片；标注超过三四个就失去指向性；alt 要描述状态与动作而不是写"截图"。这些都写成阶段 5 可检查的项。

### 为什么不带代码扫描脚本

评估过做一个 `inventory_features.py` 扫路由 / i18n / 守卫 / 校验。没做的原因：框架太多、每个框架的写法变化太快，脚本的维护面会远大于收益；而 Grep + 查找表在 agent 手里已经够用。1.0 先把流程跑通，`evidence-sources.md` 的查找表就是将来脚本的规格。

### 为什么零写操作

界面验证天然想"点一下试试"。对非本地、非测试环境，任何创建 / 删除 / 支付都可能污染真实数据。规则与 `website-clone-functional` 一致：点任何按钮前先 `browser_snapshot` 确认它不是写按钮；危险操作只截确认框再取消；只有用户确认是测试环境才真做。

### 边界

不写 API / 开发者文档、不写 PRD / 信息架构（`website-clone-functional`）、不改产品代码。读者是最终用户与管理员。
